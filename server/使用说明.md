# 粉丝团打卡：纯 CLI 服务器使用说明

适用版本：2.4.2。服务器不需要图形界面、抖音 App、浏览器或 Electron；需要 Node.js 24 或更新版本。登录和验证码在你的 Windows 电脑上处理，服务器使用导出的认证执行。

下面的部署命令按 **Linux / Bash** 编写。`node checkin-cli.js ...` 命令同样可在 Windows Server 命令行运行；后台服务部分使用 Linux systemd。

**实测范围：**独立 Node 已成功读取全部 48 个粉丝团及其签到状态；电脑端已验证一次普通签到和回读。服务器端真实签到提交尚未单独实测。示例时间只是配置示例，本说明不会替你启动任务。

## 1. 先在电脑上导出认证

打开新版“抖音整理箱”，依次操作：

1. 工具箱 → **粉丝团打卡**。
2. 点击 **登录抖音**，在软件的抖音窗口完成登录。
3. 回到打卡页面，点击 **连接当前账号** → **检查认证**。
4. 确认账号正确后，点击 **导出服务器认证**，保存为 `credentials.json`。

这个文件含登录 Cookie，服务器靠它识别你的账号。无需自己找 Token；分享链接里的 `token` 不能替代它。认证到期后重新导出即可，不需要删除打卡记录。

## 2. 准备服务器目录

先检查服务器环境：

```bash
node --version
node -e "require('node:sqlite'); console.log('SQLite OK')"
```

版本应为 `v24.x` 或更新，第二条应显示 `SQLite OK`。若提示找不到 `node`，先安装适合服务器系统与架构的 Node.js；本包不附带服务器运行时，不需要执行 `npm install`。

在当前 Linux 用户下准备一个固定目录：

```bash
mkdir -p "$HOME/douyin-checkin"
cd "$HOME/douyin-checkin"
```

将服务器 ZIP 解压后的**文件夹内容**上传到该目录，并上传电脑导出的 `credentials.json`。可以用你习惯的 SFTP 工具，不要求服务器有桌面。

最终目录应类似：

```text
douyin-checkin/
  checkin-cli.js
  checkin-domain.js
  checkin-schedule.js
  checkin-service.js
  checkin-store.js
  checkin-wire.js
  config.example.json
  credentials.example.json
  credentials.json          ← 从电脑导出的真实认证
  checkin.service.example
  README.md
  使用说明.md
```

不要只上传 `checkin-cli.js`；其余 JavaScript 模块也需要。`credentials.example.json` 是占位示例，不能用来登录。

首次创建配置：

```bash
cp -n config.example.json config.json
chmod 600 credentials.json config.json
```

后续命令都在这个目录执行。不要把认证文件放进公开网站目录、日志或代码仓库。

## 3. 首次只读检查

```bash
node checkin-cli.js --config config.json --check-auth
```

成功输出类似：

```json
{"status":"authenticated","owner_uid":"你的内部UID"}
```

这里应是当前登录账号的内部 UID。随后读取粉丝团名单与当天状态：

```bash
node checkin-cli.js --config config.json --inspect
```

`--check-auth` 和 `--inspect` 都不会提交签到。

范围是当前账号**已加入的全部粉丝团**，不按灯牌是否点亮过滤，也不受“我的圈子”数量限制。名单和状态按接口逐项读取，通常至少需要数十秒；请求间隔不低于一秒。

## 4. 手动执行一次签到

确认账号与读取结果后，执行：

```bash
node checkin-cli.js --config config.json --once
```

每轮先刷新完整名单，再逐个检查今日状态：

| 状态 | 处理方式 |
|---|---|
| 今日已签到 | 跳过，不重复提交 |
| 普通签到可执行 | 提交一次，再回读确认 |
| 需要先加入圈子 | 标记原因并跳过，不自动加入 |
| 业务类型或状态不明 | 保留未知／不支持，不猜成成功 |
| 提交超时、返回不明确 | 先回读，不立即重发 POST |

只执行普通当日签到，不送礼、不使用补签卡、不自动入圈。灯牌是否点亮和当天是否签到是两个独立状态。

日志显示“完成”表示这一轮处理结束；不一定每个团都成功，要同时看已签到和待处理数量。

## 5. 设置每天多个指定时间点

编辑 `config.json`。下面是一份**完整配置**，可以整体替换首次创建的配置内容：

```json
{
  "version": 1,
  "credentials_file": "./credentials.json",
  "data_file": "./data/checkin.sqlite",
  "schedule": {
    "enabled": true,
    "mode": "times",
    "times": ["08:30", "12:00", "21:15"],
    "start": "09:00",
    "repeats": 3,
    "interval_minutes": 240,
    "timezone": "Asia/Shanghai"
  }
}
```

这表示每天北京时间 **08:30、12:00、21:15** 各执行一轮。时间点可以不等间隔；只修改 `times` 就能换时刻。时间必须是 `HH:mm`，例如 `08:05`；重复时点自动合并，最多 24 个。

`mode: "times"` 时，`start`、`repeats` 和 `interval_minutes` 不用于生成执行时刻，保持示例值即可。**原始示例的 `enabled` 为 `false`，需要改成 `true` 才会定时签到。**

若想按间隔执行，只替换配置里的 `schedule` 对象，例如：

```json
{
  "enabled": true,
  "mode": "interval",
  "times": ["08:30", "12:00", "21:15"],
  "start": "08:00",
  "repeats": 3,
  "interval_minutes": 180,
  "timezone": "Asia/Shanghai"
}
```

这表示 **08:00、11:00、14:00**；间隔模式不使用 `times` 生成时刻。次数为 1–24，间隔为 1–1440 分钟，组合不能跨到次日。

先在前台运行定时模式，查看打印的时间预览：

```bash
node checkin-cli.js --config config.json --daemon
```

到点才执行；若启动时正处于某个时点后的五分钟内，也可能立即触发。进程每 15 秒检查配置。停机超过五分钟触发窗口的时点不追补，等下一个时点核查并补做。

每天多次运行用于补漏，已签到的会跳过。只有配置文件不会自动运行，`--daemon` 进程必须保持启动。

## 6. 关闭 SSH 后继续运行、开机自启

Linux 服务器支持 systemd 时，推荐交给它管理。使用当前普通 Linux 用户部署，先确保前面的命令可以正常运行。

如果前台 `--daemon` 正在运行，先按 **Ctrl+C** 停止它，再创建服务。以下命令在程序目录执行，会自动填写当前用户名、目录和 Node 的实际路径：

```bash
checkin_node="$(command -v node)"
checkin_dir="$(pwd -P)"
checkin_user="$(id -un)"

cat > douyin-checkin.service <<EOF
[Unit]
Description=Douyin fanclub daily check-in
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=$checkin_user
WorkingDirectory="$checkin_dir"
ExecStart="$checkin_node" "$checkin_dir/checkin-cli.js" --config "$checkin_dir/config.json" --daemon
Restart=on-failure
RestartSec=60
TimeoutStopSec=90
UMask=0077
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
EOF

sudo install -m 644 douyin-checkin.service /etc/systemd/system/douyin-checkin.service
sudo systemctl daemon-reload
sudo systemctl enable --now douyin-checkin.service
```

`enable --now` 会启动服务并设置开机自启。配置中 `enabled: true` 时，服务会按指定时点执行签到。

常用维护命令：

```bash
# 查看运行情况
sudo systemctl status douyin-checkin.service --no-pager

# 查看最近 100 行日志
sudo journalctl -u douyin-checkin.service -n 100 --no-pager

# 持续看日志，Ctrl+C 只退出看日志
sudo journalctl -u douyin-checkin.service -f

# 暂停服务，保留配置和记录
sudo systemctl stop douyin-checkin.service

# 再次启动
sudo systemctl start douyin-checkin.service

# 停止并取消开机自启
sudo systemctl disable --now douyin-checkin.service
```

改 `config.json` 后无需重启，下一轮自动读取；正在进行的一轮不会因此立刻停止。需要立即暂停时用 `systemctl stop`。

如果移动程序目录或升级后 Node 路径变化，重新生成服务文件并执行 `daemon-reload`、`restart`。没有 systemd 的服务器，可以让现有进程管理器运行同一条 `node ... --daemon` 命令；仅在 SSH 前台启动不能保证断开连接后继续运行。

## 7. 认证到期后替换

没有可信的固定有效期；以 `--check-auth` 及实际请求结果为准。认证失效后按以下顺序操作：

1. 服务器先停止常驻服务：`sudo systemctl stop douyin-checkin.service`。
2. 在 Windows 软件的抖音窗口重新登录，连接同一个账号，检查认证。
3. 再次“导出服务器认证”，把新文件上传到程序目录，先命名为 `credentials.new.json`。
4. 在服务器执行：

```bash
chmod 600 credentials.new.json
mv -f credentials.new.json credentials.json
node checkin-cli.js --config config.json --check-auth
```

认证通过后，继续原断点：

```bash
node checkin-cli.js --config config.json --resume
```

任务正常结束后，再启动常驻：

```bash
sudo systemctl start douyin-checkin.service
```

**不要删除 `data/checkin.sqlite`**，它保存历史和断点。替换认证不会清空这些记录。若导出的是另一个账号，按 UID 隔离读取新账号记录，不会接着替原账号签到。

## 8. 出现验证码怎么办

服务器不能显示验证码。先停止服务，在电脑软件的抖音窗口人工处理；必要时点击“检查认证”或继续原任务以显示实际验证页面。完成后重新导出认证，按上一节替换服务器文件，再执行：

```bash
node checkin-cli.js --config config.json --check-auth
node checkin-cli.js --config config.json --verified
```

`--verified` 会等待五秒，再检查并继续。它不代替人工验证，也不保证电脑上通过后服务器一定解除限制。仍要求验证就保持暂停；不要用普通 `--resume` 绕过等待。

若上一轮是只读 `--inspect`，恢复仍是只读核查；核查完成后要签到，另执行 `--once`。若没有任何历史任务，`--verified` 会提示没有可继续的任务。

## 9. 查看每个粉丝团的结果

终端日志显示进度与汇总，逐项结果在 SQLite 中。在程序目录运行以下只读命令，导出**当前认证账号的最近一轮结果**：

```bash
node - <<'NODE'
const fs = require('node:fs');
const path = require('node:path');
const { DatabaseSync } = require('node:sqlite');
const config = JSON.parse(fs.readFileSync('config.json', 'utf8'));
const auth = JSON.parse(fs.readFileSync(path.resolve(config.credentials_file), 'utf8'));
const db = new DatabaseSync(path.resolve(config.data_file), { readOnly: true });
try {
  const row = db.prepare('SELECT data FROM checkin_runs WHERE owner=? ORDER BY rowid DESC LIMIT 1').get(auth.owner_uid);
  if (!row) throw new Error('这个账号还没有运行记录');
  const run = JSON.parse(row.data);
  fs.writeFileSync('result-latest.json', JSON.stringify(run, null, 2));
  console.table(run.items.map(item => ({
    '主播': item.club.name,
    '状态': item.state,
    '记录日期': item.calendar?.day || '未知',
    '连续天数': item.calendar?.streak ?? '未知',
    '说明': item.message
  })));
  console.log('已导出 result-latest.json');
} finally { db.close(); }
NODE
```

这段命令不请求抖音、不提交签到，不导出认证 Cookie。数据库尚未创建时，请先执行一次 `--inspect`。`signed` 是该条记录日期已签到，不代表今天一定已签到；看结果时同时核对日期。

## 10. 常见情况

| 现象 | 原因与处理 |
|---|---|
| 提示找不到 `node:sqlite` | Node 版本不符合要求，检查 `node --version`；服务的 Node 路径也要正确 |
| 提示找不到 JavaScript 模块 | 只上传了入口文件或文件不全，请上传完整服务器包 |
| 配置、认证不可用 | 检查 JSON 语法、文件路径、权限；不要直接使用示例认证 |
| 认证 UID 不一致 | 导出了其他账号的登录状态，在电脑确认账号后重新导出 |
| 定时没有执行 | 检查 `enabled`、北京时间时点、服务状态；上轮暂停也会阻止自动新建任务 |
| 软件显示“已点亮”，但没有“今日已签到” | 点亮灯牌不等于签到，按日历判断 |
| “需要先加入圈子” | 官方入口要求先入圈，程序没有执行额外加入；是否加入由你自行决定 |
| 接口空响应／网络中断 | 最多额外重试两次；连续三个团读取失败会暂停，检查后手动继续 |
| 返回限流 | 保留断点并暂停，稍后人工重试；不要反复启动多个进程 |
| `--resume` 完成但仍有失败项 | 断点续传先处理尚未走完的部分；整轮结束后用 `--once` 刷新全名单重试，已成功的跳过 |
| SSH 断开后不运行 | 使用 systemd 或现有进程管理器，单独前台 `--daemon` 不等于后台服务 |
| 出现 `ExperimentalWarning` | 可能是运行时对 SQLite 的提示；是否失败应结合实际错误和退出码判断 |

查看上一条命令退出码：`echo $?`。0 表示正常结束，2 表示单次任务暂停，1 表示启动或执行异常；0 仍可能包含需处理项目。

## 命令速查

| 参数 | 用途 |
|---|---|
| `--help` | 查看帮助 |
| `--check-auth` | 只检查认证与身份 |
| `--inspect` | 只读取完整名单和签到状态 |
| `--once` | 刷新名单并执行一轮普通签到 |
| `--resume` | 继续最近一轮；保留原先只读／签到模式 |
| `--verified` | 人工完成验证后等待五秒再继续 |
| `--daemon` | 保持进程运行，按配置时点触发 |

每次选择一种运行模式，不要把 `--once` 和 `--daemon` 写在同一条命令里。可通过 `--config /绝对路径/config.json` 指定配置；凭据和数据库的相对路径按配置文件所在目录解析。

同一数据库有账号进程锁和时点去重记录。不同设备不会共享本地锁，建议同一抖音账号只在电脑或服务器其中一端启用定时。


## QQ 邮件失败告警（2.4.2）

无需可视化界面，也无需第三方发信服务。程序直连 QQ SMTP（smtp.qq.com，465，TLS）。需要自己的 QQ／Foxmail 发件地址、SMTP 授权码以及收件地址；在 QQ 邮箱设置中开启 SMTP 并获取授权码，不能填写 QQ 登录密码。

在 config.json 中添加或修改 email 段，其余配置保持原样：

```json
"email": {
  "enabled": true,
  "from": "your-account@qq.com",
  "to": ["recipient@example.com"],
  "credentials_file": "./mail-credentials.json",
  "cooldown_minutes": 60,
  "include_unavailable": false
}
```

把 mail-credentials.example.json 复制为 mail-credentials.json。默认示例从 QQ_SMTP_AUTH_CODE 环境变量读取授权码。无交互服务环境推荐直接在私有文件中填写（请用编辑器填写，不粘贴到日志）：

```json
{
  "version": 1,
  "from": "your-account@qq.com",
  "auth_code": "在本地填写SMTP授权码"
}
```

如果使用 auth_code，删除示例的 auth_code_env；两者同时存在时以环境变量为准。服务运行用户需要能读取文件，Linux 设置权限：

```bash
chmod 600 config.json mail-credentials.json
node checkin-cli.js --config config.json --test-mail
```

--test-mail 只发送一封测试邮件，不连接抖音、不签到，也不需要抖音认证文件有效。该命令是你主动发送的测试；即使自动告警开关关闭仍可测试。输出 sent 表示 QQ 邮箱已接受，需查看收件箱及垃圾箱；不保证实际入箱。

- 自动告警默认关闭。启用后，普通签到失败、认证失效、验证码和限流等产生每轮汇总。inspect 和 check-auth 不触发自动邮件，主动暂停和切换账号不报告。
- unsupported／needs_join 默认不发，可设 include_unavailable 为 true。不会自动加入圈子或额外付费。
- 同账号、同日、同类问题按 cooldown_minutes 去重；范围 10～1440 分钟。后续执行或 daemon 检查发现问题仍在，且间隔已过，才再次提醒。没有单独的邮件后台定时进程。
- SMTP 断线后若无法确认已收件，记录为 unknown，保持不自动重复发送同一告警。明确发信失败记录 failed，可检查配置后主动测试；打卡任务状态与邮件状态分开。
- 收件人最多 5 个。告警包含账号 UID、日期、任务状态及最多 50 个失败粉丝团名称；不包含 Cookie、授权码、接口原文或临时 URL。
- 替换凭据时，在服务器本地编辑 mail-credentials.json 并原子替换。程序每次发信重新读取。若改环境变量，需更新服务环境并重启 daemon；已运行进程不能自动继承你在另一终端修改的环境变量。
- QQ 授权码与抖音 credentials.json 独立，任一失效均可分别替换，无需删除 SQLite。桌面和服务器不共享授权码或发信去重记录。
- CLI 输出配置、认证错误时不会打印凭据。如果 config.json 本身无法解析，程序无法确定收件人，只能写本地错误日志。请确保服务可访问 QQ 的 465 端口，检查主机或云服务商的出站限制。

本次使用模拟 SMTP 检查成功接收、认证失败、明确拒绝、断线及超时，没有连接真实邮箱发送。请配置后手动执行测试命令确认。
